# Internal Windows signing

This is a **test-only** Authenticode workflow for the Windows maintenance launcher.
It does not replace production signing, signed release manifests, signed licenses
or real Windows installation acceptance. It does not create a test machine.
Do not run installation/repair/uninstall on the development laptop.

The key stays non-exportable in the signing user's Windows `CurrentUser\My`
certificate store. Only a public `.cer` and public metadata are written to disk.
No PFX, password argument, network timestamp request or automatic trust import is
used. This key is separate from the offline license/release signing keys.

## 1. Create a test publisher certificate

Run on Windows using Windows PowerShell 5.1. Choose a **new** output folder under
an existing private publisher directory with protected ancestors. Shared-writable
checkouts or network/reparse paths are refused; do not weaken their ACL checks.

```powershell
pnpm signing:internal -Action Create -CertificateDirectory C:\PrivatePublisher\InternalCertificate
```

Confirm the prompt. The output gives the public certificate path, certificate
SHA-256, store thumbprint and expiry (six months). Preserve the public metadata;
it is not a private-key backup. This implementation deliberately does not export
the private key. Losing the signing Windows account/key requires a new internal
certificate and a newly built launcher. It does not change production key custody.

## 2. Build the launcher with that exact public certificate

Use an already verified, sealed bundle and approved release public keys:

```powershell
pnpm bundle:launcher --bundle C:\PrivatePublisher\SealedBundle --trust C:\PrivatePublisher\release-public-keys.json --output C:\PrivatePublisher\NewMaintenance --certificate C:\PrivatePublisher\InternalCertificate\internal-code-signing.cer
```

The internal certificate is pinned in the executable. Its window explicitly says
**INTERNAL TEST ONLY**. Public certificate trust alone cannot make a launcher
built with a different pin usable. The unsigned UI-test executable generated by
`Test-WindowsLauncher.ps1` is not a real runtime bundle and cannot be used here.

## 3. Sign that candidate

Replace the placeholders with values from `internal-signing.json`; SHA-256 and
the Windows store thumbprint are different identifiers.

```powershell
pnpm signing:internal -Action Sign -OutputDirectory C:\PrivatePublisher\NewMaintenance -Thumbprint <STORE_THUMBPRINT> -ExpectedSha256 <CERTIFICATE_SHA256>
```

The tool checks the embedded internal label/pin, unchanged unsigned build hash
and runtime inventory. It signs only the fixed launcher, not arbitrary files.
`internal-signing.jsonl` outside the runtime records started/completed signature
creation with file hashes. Existing signatures/attempts are not silently reused
or overwritten. Retain interrupted output for inspection and build a new candidate
when necessary. No automatic rollback or re-signing is attempted.

Signature creation **does not mean Windows trusts the certificate**. The original
build report still describes the unsigned build; the separate signing receipt
describes the signing attempt. Verification is an explicit next step.

## 4. Trust and verify only on the isolated test account

This step remains postponed until a disposable Windows host is available. Copy
the public certificate and the complete signed maintenance folder there. Never
copy the private key. Verify the certificate SHA-256 with the publisher through a
separate channel before trusting it.

Using the publisher/operator tooling on that test machine:

```powershell
pnpm signing:internal -Action Trust -CertificateFile C:\TestInputs\internal-code-signing.cer -ExpectedSha256 <INDEPENDENTLY_CONFIRMED_CERTIFICATE_SHA256> -TestMachine
pnpm signing:internal -Action Verify -OutputDirectory C:\TestPublisher\NewMaintenance -ExpectedSha256 <CERTIFICATE_SHA256>
```

The commands can also run directly with
`& ./scripts/issuer/Internal-WindowsSigning.ps1` instead of `pnpm signing:internal`;
no Node/pnpm is needed for the PowerShell signing commands. These are developer/
test-operator tools and are excluded from customer distributions.

Trust is explicit, confirmed and scoped to **CurrentUser\Root**, not the whole
machine. Use the same Windows account for verification and elevation. If UAC
uses a different administrator account, it needs its own explicitly approved test
trust. This tool never trusts other accounts automatically. Windows application
control/SmartScreen policies may still restrict internal test executables; no
policy bypass is implemented.

`Verify` requires Windows Authenticode status **Valid**, the exact certificate
pin, current certificate validity and intact runtime inventory. Native host
actions still perform their existing Windows signature, pinned publisher, ACL,
inventory and administrator checks. Only after verification should the signed
launcher be used for the documented disposable-host acceptance tests. Self-signing
does not prove those tests passed.

## 5. Remove internal trust after testing

On each test account where it was explicitly installed:

```powershell
pnpm signing:internal -Action RemoveTrust -CertificateFile C:\TestInputs\internal-code-signing.cer -ExpectedSha256 <CERTIFICATE_SHA256> -TestMachine
```

This removes only the exact confirmed certificate from that account's Root store;
it also works after expiry. Do not remove unrelated certificates. When the test
signing key is no longer needed, the publisher can remove its exact My-store
certificate and private key after checking its thumbprint:

```powershell
Remove-Item -LiteralPath 'Cert:\CurrentUser\My\<EXACT_INTERNAL_STORE_THUMBPRINT>' -DeleteKey -Confirm
```

Existing internal signatures expire with their certificate: no timestamp service
is used. Renew by creating a new certificate, rebuilding with its public pin,
signing, and explicitly approving the new certificate on test accounts.

## Safe automated verification

```powershell
& ./scripts/issuer/Test-InternalWindowsSigning.ps1
```

The test creates an ephemeral non-exportable My-store key, signs a native fixture,
checks pin/overwrite/tamper rejection and untrusted verification denial, and deletes
that exact test certificate/key in `finally`. Trust/removal run only with `WhatIf`;
the test verifies that the current user's Root store is unchanged. It never runs
the signed launcher or installs product services. Small **public** evidence
fixtures are retained in a unique private LocalAppData directory. Actual trusted
verification, UAC account behavior and host operations remain test-machine checks.
